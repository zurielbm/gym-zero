Plan · Gym Tracker

Complete UI Redesign

A ground-up visual redo of the workout + food tracker. Three distinct design directions below, each mocked in mobile and desktop form, followed by the implementation plan. The data layer (DataAPI / Dexie) is untouched — this is a UI-only rebuild.

Current state Design 1 · Nightlift Design 2 · Daybook Design 3 · Ignite Comparison Implementation plan Q&A

Where the UI is today

The app is a single 460px column that simply gets centered on desktop — there is no desktop layout at all. All styling lives in one styles.css with ad-hoc class names; screens are 8 React components behind a hand-rolled screen switcher.

TabBar (4 tabs)→ Home Routines → Workout → Summary Scan → Machine Food History

8 screens, one shell, one stylesheet (~270 lines), FAB for QR scan on workout screens, rest-timer toast. Current palette: near-black blue #0d1117, mint #66e3a4, periwinkle #74a7ff.

What the redo must keep working: routine-based set logging with previous-weights prefill, QR scan → machine video, calorie/protein rings and quick food logging, week activity + PR history, rest timer, offline/IndexedDB. What it adds: a real desktop experience (multi-pane layouts, sidebar navigation) instead of a centered phone column.

Desktop · Dashboard with sidebar

Why pick Nightlift.

Lowest-risk restyle — it modernizes what exists without changing the app's personality. Dark suits the actual use context (phone in a gym). The desktop dashboard falls out naturally: the sidebar replaces the tab bar, and Home cards become a grid. Trade-off: it's the least dramatic "redo" of the three; if you want the app to feel brand-new, look at Daybook or Ignite.

Design 2 — Daybook

Reinvention

Light

Editorial / paper

A complete personality change: a warm paper-toned light theme with serif display headings, hairline dividers instead of heavy cards, and one confident forest-green accent. Feels like a well-kept training journal — calm, legible in daylight, great for the food-logging half of the app. Desktop uses a centered reading column under a simple top nav.

Desktop · Two-pane workout (list + logger + form video)

Why pick Daybook.

The most complete reinvention and the strongest desktop story — the two-pane workout view (exercise list on the left, logger and form video on the right) makes desktop genuinely better than mobile, not just wider. Light theme is more pleasant for food logging and reading history at home. Trade-off: light UIs are harsher on the eyes mid-workout in a dim gym; if you choose Daybook we should consider keeping a dark mode toggle (extra effort, noted in the plan).

Desktop · Scoreboard grid

Why pick Ignite.

Maximum personality and motivation — the app feels like gear, not a form. Big numerals are extremely glanceable mid-set, and the flat, borderless style is actually the simplest CSS of the three. Trade-off: bold typography is unforgiving — spacing and hierarchy must be exact or it looks broken, and the aesthetic can fight dense screens like Routines editing. Needs a proper condensed display font (e.g. Archivo Expanded/Anton via one self-hosted woff2) to land.

Implementation plan

The same 5 phases apply to whichever design wins — only Phase 2/3 content differs. Everything below src/data/ and src/types.ts stays frozen; the redo touches styles.css, App.tsx, components/, and screens/.

Phase A · Foundations

Design tokens + responsive shell

  • Replace the ad-hoc :root vars with a full token sheet (color, space, radius, type scale) in a new src/theme.css — the chosen design is expressed entirely as tokens so future reskins are cheap.
  • Rebuild the shell: <768px keeps the phone column + bottom tab bar; ≥768px switches to the design's desktop chrome (sidebar or top nav) with a fluid content area — this kills the current hard 460px cap.
  • Screen switcher stays (no router dependency needed), but the shell exposes a wide flag so screens can render multi-pane desktop variants.
Phase B · Component kit

Rebuild the 12-piece component library

  • Buttons (primary/ghost/icon), Card, Chip, Field/Input, Ring, ProgressBar, SetRow grid, TabBar/SideNav, RestToast, FAB/ScanKey, CalendarStrip, Sparkline — restyled to the chosen direction, same props as today so screens swap cleanly.
  • Ignite only: wire the condensed display font (single self-hosted woff2, font-display: swap).
Phase C · Screens, mobile-first

Migrate all 8 screens

  • Order: Home → Workout → Routines → Food → History → Summary → Scan → Machine (highest-traffic first; Scan/Machine last since the viewfinder styling is self-contained).
  • Each screen lands in its own commit so any regression bisects to one screen.
Phase D · Desktop layouts

Make wide screens genuinely better, not just wider

  • Home: dashboard grid (rings + volume chart + last workout + week strip together).
  • Workout: two-pane — exercise list left, active logger + form video right (Daybook mock above shows the pattern; all three designs get it).
  • History: calendar/sparkline left, selected-session detail right.
  • Food: day log left, quick-add + saved meals right.
Phase E · Polish + verification

Motion, edge cases, and the existing test gates

  • Screen transitions, ring/ bar animations, rest-toast entrance; reduced-motion respected.
  • Empty states (no workouts yet, empty food day), long routine names, 44px touch targets, safe-area insets re-checked.
  • Gates: npm run typecheck, npm run build, and the existing npm run e2e flow must pass unchanged — it exercises the full log-a-workout path, so it doubles as the refactor safety net. Manual pass on a real phone via the LAN dev URL.

Sequencing note: A → B → C are strictly ordered; D can start per-screen as each screen clears C; E is continuous but has a final dedicated pass.

Q&A — what I need from you

1. Which direction do we build?

Nightlift (refined dark) · Daybook (light editorial) · Ignite (bold athletic) — or a mix (e.g. "Ignite's typography on Nightlift's palette").

Why I'm asking: everything in Phases B–D is styled to one direction; picking after work starts means redoing the component kit. Mixing is fine but tell me which design is the base. The mockups above are the decision artifact — look at each pair on your phone and monitor.

2. If Daybook: do you need a dark mode too?

Daybook is light-first. A companion dark theme is ~1 extra day since Phase A tokenizes all color, but it's still extra surface to test.

Why I'm asking: you use this in the gym, often in dim light, phone at max brightness between sets. If you train in a bright LA Fitness this is a non-issue; if not, light-only could be a daily annoyance. Nightlift/Ignite make this question moot.

3. How much do you actually use desktop?

(a) Rarely — just make it not-embarrassing (keep centered column, nicer chrome) · (b) Sometimes — full Phase D as planned · (c) Often — Phase D first-class, consider keyboard shortcuts for set entry.

Why I'm asking: Phase D (multi-pane desktop layouts) is roughly a third of the total effort. The app is offline/IndexedDB per-device with no sync (Phase 3 of the product roadmap isn't built), so desktop currently shows different data than your phone — worth confirming desktop investment is wanted before sync exists.

4. Keep the 4-tab structure (Home / Workout / Food / History)?

All three mocks keep today's information architecture — this is a reskin+responsive redo, not a nav redesign. Ignite's mobile mock adds one change: the QR scan gets a permanent center slot in the tab bar instead of a floating button.

Why I'm asking: "redo the whole UI" could mean visuals (assumed here) or also flows. If you want flow changes — e.g. merging Food into Home, or scan-first navigation — that's a scope add I'd fold into Phase C per screen.
